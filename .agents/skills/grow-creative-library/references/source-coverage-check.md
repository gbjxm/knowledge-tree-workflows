# 来源内容登记检查

在来源笔记写完、完成逐段语义复核后运行本检查。它与 `validate_note.py` 分开：原验证器继续检查笔记结构，本命令只检查覆盖登记是否闭合、来源与笔记版本是否一致、定位是否有效。它不判断内容项是否列全，不证明语义保全、事实准确或视频画面覆盖，也不输出知识覆盖百分比。

## 只读命令

```powershell
python -B -X utf8 scripts/check_source_coverage.py --source '<源文本或转写路径>' --note '<笔记路径>' --coverage '<覆盖清单JSON路径>'
```

默认输出 JSON 到 stdout；`--format text` 输出便于阅读的报告。命令不修改输入或状态、不自动生成清单、不联网。退出码：`0` 登记闭合但仍需语义复核；`1` 有待补、待核或未登记区间；`2` 输入／清单无效。缺少新清单的旧笔记继续走原结构检查，不能因此声称内容检查通过。

每次绑定一份源文本与一篇笔记。多篇笔记分别检查，可共用同一源文本并声明不同 `scope`。PDF 先形成 UTF-8 提取文本，保留页码分隔；视频用带时间码转写；文章保留标题／段落。不要把二进制 PDF 或媒体直接传给 `--source`。

## 最小清单

工作清单可保存在配置的库外缓存；复核后明确采用的长期记录按 [长期来源复核记录](durable-source-evidence.md) 保存到配置的 `source_evidence`，原始文本与媒体仍留缓存。笔记只保留范围、缺口与记录入口。SHA-256 针对两份输入的原始文件字节，可用 `Get-FileHash -Algorithm SHA256 -LiteralPath '<路径>'` 取得。修改来源或笔记后必须重新核对映射，再更新哈希，不能只换哈希强行通过。

```json
{
  "version": 1,
  "source_sha256": "填入源文本文件的64位SHA256",
  "note_sha256": "填入笔记文件的64位SHA256",
  "scope": [[5, 22]],
  "items": [
    {
      "id": "U01",
      "item": "空间狭窄时删去侧面机位的条件和庭院案例",
      "source": {"lines": [5, 12], "quote": "原材料中的确切片段"},
      "note": {"lines": [35, 40], "quote": "笔记中的确切片段"},
      "status": "保留"
    },
    {
      "id": "U02",
      "item": "指向画面的机位变化示范",
      "source": {"lines": [13, 22]},
      "status": "待核",
      "reason": "转写中的指代依赖原画面，当前没有取得对应帧。"
    }
  ]
}
```

- `scope` 和 `lines` 是 1 起算、两端包含的行号；`scope` 只写本次真正核对的范围，可有多个区间。若正文之外有标题、说话人标签或页码行，可并入所属单元范围，不能为获得闭合而悄悄缩小约定范围。
- `id` 唯一；`item` 说明观点、论证、方法、案例或限定条件。定位允许重叠，多个单元也可合并到同一笔记段。
- `status` 仅用 `保留`、`合并`、`待补`、`待核`；`合并`、`待补`、`待核` 必填 `reason`。`保留/合并` 必须有 `note` 定位，另两者允许省略。
- `quote` 可选；如填写，须在对应行段内找到确切片段。它可防止定位偏移或特定限定语消失，不能证明整个论证正确；合理改写需人工核对后更新片段。
- 命令自动报告 `scope` 中尚未登记的非空行区间。一个宽行段登记闭合仍可能漏掉段内第二个案例或限定条件；不能为了关闭区间，把无关内容全部圈进一项。

## 三种检查的边界

1. **机器检查**：哈希、行号、确切片段、重复 id、状态／理由与登记缺口。
2. **AI 语义复核**：顺着原材料核对内容清单，再对笔记检查因果、案例推导、说话者、确定程度与限定条件。另开一遍同模型复核不称为独立验证。
3. **用户样本审阅**：看一个代表章节是否细节充足、结构易读、未来能够使用。尚未完成的用户审阅不得写成已验收。
